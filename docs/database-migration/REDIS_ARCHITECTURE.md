# Redis architecture

## Deployment choice

The production audit found no Redis service. Prepare a small self-hosted Redis on the existing Hostinger Docker network; it adds no paid subscription. The supplied Compose overlay has no published host port, a named ACL user, bounded clients, 128 MiB maxmemory, 192 MiB container memory and 0.25 CPU. The official Redis 8 multi-platform image is pinned to the immutable digest recorded in `redis-image.json`; review that digest during staging. Redis Cloud/managed Redis offers independent availability but requires service/region/cost selection; Upstash requires an actual compatible TCP endpoint for this ioredis/Fastify integration, not merely an HTTP REST API. No provider was purchased or provisioned.

The chosen single-host Redis shares the VPS failure domain. Use TLS (`rediss://`) for remote services. The provided private Docker network is the only planned TLS exception (`REDIS_PRIVATE_NETWORK=true`); it requires ACL authentication and a verified unexposed port. Never permit a public 6379 listener. Inspect actual remaining host memory before starting it.

## Shared infrastructure

`server/src/infrastructure/redis/service.ts` merges separately supplied authentication into its internal connection URL before constructing ioredis, and centralizes one command client and one subscription client, timeouts, bounded retries, jittered reconnection, no unbounded offline queue, safe diagnostics and shutdown. Prefix keys with deployment/version (`meldiq:production:v1`); scope components are hashed with JSON boundary encoding to prevent separator collisions. Every cache/coordination key expires. A maximum of 64 connections and 1000 in-process cache fills bound resource use.

- **Cache-aside preferences**: user + community scoped, 15-second TTL, maximum 64 KiB, validated preference records only (saved-message identifiers, no bodies). Routes authenticate and check current membership before the cache. Mongo conditional revision writes remain authoritative. Successful writes and every deletion rotate a shared generation token; slow prior reads cannot populate the current generation. Cache-fill requests collapse within the API process. Generation tokens expire after one day; entries expire within 60 seconds. Failed invalidation bypasses that process's cache for 60 seconds; another process can retain at most the 15-second display-only TTL. Permissions, authentication decisions, revocation and subscription entitlements are never cached.
- **HTTP limits**: the existing Fastify rate limiter uses the shared client, keyed by authenticated user or IP/IPv6 /64, including route overrides. An additional atomic per-network budget is ten times the global per-user allowance. Redis failures return retryable 503 rather than multiplying budgets through a local fallback. Existing domain-specific in-memory anti-abuse windows remain supplementary and must be ported before multiple API writers are permitted. Health is exempt and reports Redis failure with 503.
- **Presence**: per-user sorted-set leases, unique device/socket lease members, 90-second expiry, refreshed on WebSocket pong; closing one socket does not remove another socket's lease. Server crash is cleared by expiry. `isPresent` is available to shared coordination; current public presence visibility/privacy and settled online/offline behavior stay in the local hub until a fully distributed hub is implemented.
- **Typing**: verified conversation membership before storing a five-second indicator; explicit stop deletes it. No message content is stored.
- **Pub/Sub**: committed preference updates publish user/community/revision metadata; other listeners notify local sockets. Failed delivery is recovered by a normal preference fetch. Redis Pub/Sub is not durable history or a queue. The relay-wakeup API is reserved for future fan-out and is not an implemented distributed hub.
- **Jobs**: no critical work is moved into Redis. Existing relay delivery, reminders/occurrences, provider events, pending blob deletes and retries stay in the durable owning Mongo domain after its cutover. Business idempotency and recovery remain in their existing services.

Memory policy is `noeviction`, so active abuse counters cannot disappear under cache pressure. Expired keys reclaim space; cache writes may fail safely, and admission fails closed if no new counter can be allocated. Critical queues require a separate workload/service and durable Atlas metadata if introduced. Monitor INFO memory, hit/miss/error metrics, client count and health; admin infrastructure shows aggregate memory and cache usage. No plaintext messages, private keys, account passwords, or bearer/refresh tokens are written to Redis.

References: [Redis ioredis guide](https://redis.io/docs/latest/develop/clients/ioredis/), [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/), and the installed @fastify/rate-limit README (requires ioredis for distributed limits).

The actual pinned-image rehearsal caught and fixed ioredis URL-password precedence: an empty URL password overrode REDIS_PASSWORD in constructor options. The centralized client now merges that separate password into its private connection URL before constructing ioredis. The ACL integration test exercises that exact deployment configuration. The API Compose overlay also sets a reviewed 384 MiB Node heap budget with a 768 MiB API container cap on the existing VPS; preserve other required Node flags through MELDIQ_NODE_OPTIONS.
