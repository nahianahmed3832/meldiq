Windows 0.2.0 retains the old fixed origin in its installer. Its single-file fallback does not rescue an interrupted multipart transfer to a blocked host. Keep the old path available until installed-client and upload-session transition risks have been addressed. Small-file success alone cannot qualify a cutover. No Android update or web build was forced.

Windows 0.2.1 completed signed qualification and stable publication. Public feed signature, full 124,227,177-byte installer, SHA-256 and exact storefront link were checked after publication. The published bytes have SHA-256 25095025281bfbcc8d0f5b8443cd7103fafb78bd5f3d0136303b25c11f556d02. A transitional API path recognizes the published 0.1.0/0.2.0 desktop user agents. They upload directly to the previously permitted Singapore origin. The API verifies a conditional Frankfurt copy against the declared full SHA-256 before recording success. Newly supported desktops upload directly to the primary. A production synthetic exercised the actual conditional copy twice under the API identity. Source permissions, quotas and membership checks remain mandatory.

The GitHub internal-beta APK was also obtained and hash-verified against the release asset. It installed and launched on Android 16 as com.griipbuddy.message 0.1.0-beta, an earlier package distinct from the current Play listing for com.meldiq.android. The actual Play page identifies Meldiq. An unsigned bundle or the earlier GitHub release cannot substitute for a test of the currently distributed Play build.

The final public compatibility canary exercised the historical session, new Frankfurt single upload, and a simulated older Windows user agent that received a Singapore URL. All completed files were readable through the Frankfurt-backed edge. This checks the API path; it is not a complete installed-client GUI test.
