# Recovery

Frankfurt is the only application storage writer. The runtime IAM policy explicitly denies the Singapore media bucket. To reverse, use a separately authorized operator identity, fence the current writer, build and verify the reverse delta, reconcile sessions, and authorize any necessary runtime policy change. Never bypass the retention hold. Both original recovery archives and the final encrypted checkpoint are available in Frankfurt.

## Migration record

Frankfurt is now the file-storage authority. Singapore was primary before the switch. Keep the SQL/Mongo authority, local fallback, object stores and version manifests intact. Disable the optional MEDIA_PUBLIC_BASE_URL to restore the existing authenticated download path if the edge release fails. Restore nginx from the retained /opt/meldiq-web/storage-migration-headers-20261103T065311Z backup only if the installed clients no longer need the new origins. Restore the prior storefront release as an atomic link switch if necessary.

After the writer switch, a region-variable change can strand Frankfurt-only files or restore deleted media. First fence new uploads, multipart completion, retention/deletion jobs and writers in every API instance. Drain or explicitly preserve in-flight upload sessions; their presigned URLs and upload IDs belong to their original region. Keep both buckets readable. Confirm the authoritative database and a usable current backup. Run deploy/storage-migration/rollback-plan.py with the exact forward and disk journals. It refuses unexpected source changes or missing Frankfurt history. Follow the reverse-delta JSONL per key in order. Copy the specified Frankfurt versions into Singapore preserving metadata/tags, hash and compare bytes. Reproduce necessary soft markers only after reviewing their impact. Never hard-delete an existing version. Reconcile the database's live file references and disk fallback under the fence before reopening traffic. If a store is inaccessible or a manifest is inconsistent, keep the surviving writer authoritative until the delta can be recovered.

The read-only reverse plan produced zero post-baseline entries at staging and identified a Frankfurt-only change on its first post-activation run. No production writer reversal was rehearsed. The forward copier does not run against an active Frankfurt writer. Preserve the manifests and test the reverse plan again after any new writes. Do not remove Singapore data without separate explicit authorization.

The operator copied the age-encrypted version/disk journals to the existing versioned recovery bucket. Server-side AES256 and SHA-256 readback matched the encrypted artifact, and decrypting the archive with the existing recovery identity reproduced the S3 journal checksum. This protects the mapping; it is not a substitute for a backup of customer bytes written after cutover. Preserve later checkpoints separately. rollback-plan.py verifies mirrored writes for named old sessions and old-desktop IDs. It refuses unpaired or divergent histories.

The final journal archive also contains the fence, release and activation receipts and the two captured pending session IDs. Its encrypted S3 checksum matched readback and the recovered manifest matched its original SHA-256. The backup bucket applies its existing expiration policy. A fresh recovery checkpoint is required as the active writer changes.

The stack finished UPDATE_COMPLETE and S3 readback confirmed both statuses. Reenabling destructive retention requires a separate review of the retained history.
