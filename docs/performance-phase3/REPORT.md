# Meldiq Phase 3: single-writer handoff

**The proposed six-connection writer passed two independent production-sized rollout/rollback rehearsals. Production remains on `b9e6f005`; the production writer was never rotated.** The rehearsed profile needs a nine-slot application-role budget and no remaining direct sessions at takeover. The observed production role has a limit of six, and the incumbent still has direct WebSockets. Shrinking its serving pool to four worsened inbox p95 by 50% under matched load, so that configuration was rejected. This work did not replace it or change the Supabase authority. The production canary switched **only the opt-in ingress**, using a private two-member monitoring conversation. A source push is not a production writer deployment. [Production identity](production-final.json) · [Release gates](decision.json)

## What changed

The experimental gateway keeps the HTTP listener and external WebSockets alive while the single writer changes. It holds only requests that have not been sent upstream, streams normal traffic, and never retries a dispatched POST. The queue holds at most 128 requests for at most 7.5 seconds; the test client still gives each HTTP request eight seconds. It waits for actual authenticated pongs to fence earlier WebSocket frames and reauthenticates each resumed socket against the new writer. It suppresses duplicate queue rows already delivered to that same external socket. The database remains responsible for message IDs, durability, order and authorization.

A managed account can legitimately renew its access token while the original socket remains authenticated by session ID. The private drain operation now **refuses to switch** on a managed, expired, unverified or ambiguous connection. The incumbent keeps serving. A staging client rotated a real account token, received an authenticated pong before and after this veto, and then explicitly signed out its own test account. This does not prove that a managed socket can resume on a different writer with a rotated token. Existing production sockets established directly on the incumbent cannot be intercepted by installing the gateway.

The proposed writer and fallback stream startup reads and prepare the two largest tables using a retained read-only snapshot. After acquiring the exclusive writer lease, they compare the actual visible tuple positions in a fresh consistent snapshot; they reload changed pages and freshly read the other tables. Any expired snapshot or excess churn fails setup. No schema migration or production write occurs during preparation. PostgreSQL's tuple identifiers refer to physical row versions, not durable business identities. [PostgreSQL system columns](https://www.postgresql.org/docs/17/ddl-system-columns.html) · [Routine vacuuming](https://www.postgresql.org/docs/17/routine-vacuuming.html)

The production catalog showed **239 relations, approximately 673,064 rows and 79,192,064 heap bytes**. The two largest tables were telemetry samples and device delivery queues. Under a read-only diagnostic role, one shadow prepared 630,025 rows in 8.79 s before the handoff, verified the prepared rows in 2.58 s, and completed the fenced reads in 4.30 s. This was a database measurement, not a production startup. A separate parallel shared-snapshot experiment took 8.38 s and was rejected; those runs were not an alternating controlled benchmark. ## Serving capacity during standby preparation

Reducing the writer pool from six to four **failed** the predeclared p95 screen, despite zero HTTP errors. The same pinned candidate and database served eight concurrent readers in 6/4/4/6 order. Each pool had 500 measured authenticated inbox reads, 500 history reads of the same encrypted message and 40 health checks, with explicit separate warm-ups. No live requests or credentials were used. The test verified consistent inbox membership and committed history across restarts. This is a controlled read-load comparison, not a benchmark of regional production traffic or a write-capacity guarantee.

With the existing six serving connections preserved, the separate nine-slot fixture passed twice. ## Live production ingress canary

The first opt-in canary stopped on a 503 acknowledging the fourth message. All four were already durable. The public configuration was restored byte-for-byte at 13:29:33 UTC; the live writer never restarted. The operating audit records an independent maintenance change enabled at **13:29:29.676 UTC** and disabled at **13:29:54.082 UTC**. All 402 origin 503s in the observed burst fell inside that interval; 20 requests in total used the opt-in gateway. The original route subsequently acknowledged the one pending item; the four messages were confirmed by signature in history without resubmitting any of them. [Client](production-ingress-client.json) · [Operator actions](production-ingress-operations.json) · [Audit timing](audit-window.json) · [Origin status](origin-status.json) · [Reconciliation](production-reconciliation.json)

The repeated canary, with maintenance off, activated the private cohort, rolled back the route, activated it again, then restored the exact original configuration and retired the sidecar. Its 12 encrypted messages had 12 unique delivered frames, 12 committed-history verifications and 12 acknowledged queue items. Both client sockets stayed open, the duplicate-submit check returned the original timestamp, and the driver observed no error. This tested a **route** change on the unchanged writer. It did not test a production writer restart. [Signed-in canary and route receipts](production-ingress-retest.json)

A later pilot used the exact final gateway digest. Four messages completed on its opt-in route, then the next client fetch failed at the preceding Nginx configuration reload. The application logged four successful message POSTs and no error response in the interval. A read of the signed history and recipient queue found exactly four events, all acknowledged; no message was resubmitted. Neither client WebSocket reported a close. The data locate the failure around the route change; they do not identify which network hop closed the connection. [Pilot](production-verified-ingress.json) · [Origin totals](production-verified-origin.json) · [Read-only reconciliation](production-verified-reconciliation.json)

The revised operator installs one dormant, secret-header-only route. It toggles a root-controlled regular file between gate positions; the same Nginx workers select the origin on every request, and the default route stays direct. Installing and finally removing the dormant rule still require separate Nginx reloads. The isolated Nginx integration test made 120 requests on a single persistent client TCP connection, confirming both route choices and header stripping across all switches. [Isolated keep-alive receipt](hot-ingress-lab.json) · [Nginx file tests](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html#if) · [Nginx reload behavior](https://nginx.org/en/docs/control.html)

On the exact final public canary, the two activations and two rollbacks recorded the same Nginx worker generation throughout, without a reload at any switch. Both original client sockets stayed connected. Twelve encrypted messages had 12 distinct delivered frames, 12 signed history checks and 12 acknowledgements, with no errors or duplicate frames. The duplicate-submit check preserved the original timestamp. The public default stayed on the original writer, and the final retirement restored the original nginx bytes and removed the idle sidecar. This was an ingress-only pilot, not a live writer rotation. The exact controller used by both strict runs is on the [tested handoff commit](https://github.com/nahianahmed3832/meldiq/tree/9d4a49081382392108d9a62c113ef31476bebe4b/deploy/performance-phase3). The subsequent pool experiment uses a separate mode and does not overwrite either handoff receipt.

The private standby can wait on the same exclusive PostgreSQL session that the normal writer subsequently uses. Its lock timeout is bounded; the ordinary check remains in place and closing the session releases both acquisitions. [PostgreSQL advisory lock semantics](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS)

The pristine incumbent is separately retained. Its faster warm fallback has different bytes. A rollback must retain the same current PostgreSQL authority, data and volume. Never restore an older database to undo a binary release. [Final held-release decision](decision.json) · [Last production admission check](live-admission-final.json). The final three minute samples reported 4, 2 and 2 hub sockets (the newest sampled minute included the private cohort); none demonstrated a drained incumbent.

No production **after** inbox p95 exists for this candidate. The prior release's 500 measured signed-in reads per region had inbox p95 **763 ms Frankfurt, 549 ms Singapore and 683 ms Tokyo**. Neither the isolated numbers nor 12 opt-in samples qualify as a replacement regional p95. A separate one-hour origin-log window on the still-live incumbent recorded 30 successful inbox requests, p50 225 ms, p95 1,610 ms, p99 1,674 ms, with three maintenance 503s and one 401 counted separately. This is server time on mixed traffic, not comparable to the regional end-to-end measurements. [Live origin observations](live-inbox-baseline.json) Phase 3 added no recurring compute or paid CDN feature. Existing-host CPU, storage and network use were not separately invoiced. **Next production window.** Keep the running writer, exact ingress configuration, current data volume and authoritative database. Under both release locks, verify maintenance is off; confirm the image, configuration and authority receipt still match; and check actual provider capacity and live hub connections again. An idle SQL backend is not a reservation. Establish supported standby capacity without disconnecting a customer; reject a throughput regression before touching the production pool. Move new WebSocket connections behind a qualified gateway in a bounded cohort, then wait for the remaining direct connections to drain naturally. A managed or ambiguous connection behind the gateway also vetoes the switch. Rehearse the actual production controller, readiness failure and current-data fallback for that topology before stopping the incumbent. The two strict tests certify planned transitions in the tested fixture, not automatic recovery from an arbitrary crash after ownership transfers. Only a real production writer promotion would enable comparable after measurements; use the Phase 2 regional method with 500 signed-in observations per region and restore the known writer behavior on a material regression.

To repeat the opt-in pilot, use the lock- and digest-checked ingress controller only with the matching original nginx checkpoint. `rollback` restores its exact predecessor, `check` compares both versions, and `retire` removes only an idle, matching sidecar after restoration. These operations do not change the writer. The staging driver refuses the wrong image or simultaneous leases, sends during both switches, and records failed probes; its synthetic fixture settings must never be used on the production database.
