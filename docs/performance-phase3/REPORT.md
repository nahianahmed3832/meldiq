**Staging passed both independent production-sized rollout/rollback rehearsals. Public writer: b9e6f005.** This work did not replace it or change the Supabase authority. The production canary switched **only the opt-in ingress**, using a private two-member monitoring conversation. A source push is not a production writer deployment. ## What changed

The experimental gateway keeps the HTTP listener and external WebSockets alive while the single writer changes. It holds only requests that have not been sent upstream, streams normal traffic, and never retries a dispatched POST. The queue holds at most 128 requests for at most 7.5 seconds; the test client still gives each HTTP request eight seconds. It waits for actual authenticated pongs to fence earlier WebSocket frames and reauthenticates each resumed socket against the new writer. It suppresses duplicate queue rows already delivered to that same external socket. The database remains responsible for message IDs, durability, order and authorization.

A managed account can legitimately renew its access token while the original socket remains authenticated by session ID. The private drain operation now **refuses to switch** on a managed, expired, unverified or ambiguous connection. The incumbent keeps serving. A staging client rotated a real account token, received an authenticated pong before and after this veto, and then explicitly signed out its own test account. This does not prove that a managed socket can resume on a different writer with a rotated token. Existing production sockets established directly on the incumbent cannot be intercepted by installing the gateway.

The proposed writer and fallback stream startup reads and prepare the two largest tables using a retained read-only snapshot. After acquiring the exclusive writer lease, they compare the actual visible tuple positions in a fresh consistent snapshot; they reload changed pages and freshly read the other tables. Any expired snapshot or excess churn fails setup. No schema migration or production write occurs during preparation. PostgreSQL's tuple identifiers refer to physical row versions, not durable business identities. [PostgreSQL system columns](https://www.postgresql.org/docs/17/ddl-system-columns.html) · [Routine vacuuming](https://www.postgresql.org/docs/17/routine-vacuuming.html)

The production catalog showed **239 relations, approximately 673,064 rows and 79,192,064 heap bytes**. The two largest tables were telemetry samples and device delivery queues. Under a read-only diagnostic role, one shadow prepared 630,025 rows in 8.79 s before the handoff, verified the prepared rows in 2.58 s, and completed the fenced reads in 4.30 s. This was a database measurement, not a production startup. A separate parallel shared-snapshot experiment took 8.38 s and was rejected; those runs were not an alternating controlled benchmark. ## Live production ingress canary

The first opt-in canary stopped on a 503 acknowledging the fourth message. All four were already durable. The public configuration was restored byte-for-byte at 13:29:33 UTC; the live writer never restarted. The operating audit records an independent maintenance change enabled at **13:29:29.676 UTC** and disabled at **13:29:54.082 UTC**. All 402 origin 503s in the observed burst fell inside that interval; 20 requests in total used the opt-in gateway. The original route subsequently acknowledged the one pending item; the four messages were confirmed by signature in history without resubmitting any of them. [Client](production-ingress-client.json) · [Operator actions](production-ingress-operations.json) · [Audit timing](audit-window.json) · [Origin status](origin-status.json) · [Reconciliation](production-reconciliation.json)

The repeated canary, with maintenance off, activated the private cohort, rolled back the route, activated it again, then restored the exact original configuration and retired the sidecar. Its 12 encrypted messages had 12 unique delivered frames, 12 committed-history verifications and 12 acknowledged queue items. Both client sockets stayed open, the duplicate-submit check returned the original timestamp, and the driver observed no error. This tested a **route** change on the unchanged writer. It did not test a production writer restart. [Signed-in canary and route receipts](production-ingress-retest.json)

The private standby can wait on the same exclusive PostgreSQL session that the normal writer subsequently uses. Its lock timeout is bounded; the ordinary check remains in place and closing the session releases both acquisitions. [PostgreSQL advisory lock semantics](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS)

The pristine incumbent is separately retained. Its faster warm fallback has different bytes. A rollback must retain the same current PostgreSQL authority, data and volume. Never restore an older database to undo a binary release.

No production **after** inbox p95 exists for this candidate. The prior release's 500 measured signed-in reads per region had inbox p95 **763 ms Frankfurt, 549 ms Singapore and 683 ms Tokyo**. Neither the isolated numbers nor 12 opt-in samples qualify as a replacement regional p95. A separate one-hour origin-log window on the still-live incumbent recorded 30 successful inbox requests, p50 225 ms, p95 1,610 ms, p99 1,674 ms, with three maintenance 503s and one 401 counted separately. This is server time on mixed traffic, not comparable to the regional end-to-end measurements. [Live origin observations](live-inbox-baseline.json) Phase 3 added no recurring compute or paid CDN feature. Existing-host CPU, storage and network use were not separately invoiced. [Regional baseline extract](regional-inbox-baseline.json)

The observed role had six provider backend sessions for a limit of six. At 13:42 UTC the three latest minute samples all showed two incumbent sockets, with the canary removed. Ten consecutive minute samples at 13:56 UTC subsequently showed the same two existing sockets with zero connects or disconnects. [Follow-up sample](live-admission-followup.json). A prior short read-only login succeeded, so the PostgreSQL session count is an admission signal, not evidence that every pooler checkout always fails. A release must acquire its standby slots without evicting the incumbent, then wait for existing direct sockets to finish naturally. [Admission](live-admission.json) · [Single-login check](standby-admission.json)

To repeat the opt-in pilot, use the lock- and digest-checked ingress controller only with the matching original nginx checkpoint. `rollback` restores its exact predecessor, `check` compares both versions, and `retire` removes only an idle, matching sidecar after restoration. These operations do not change the writer. The staging driver refuses the wrong image or simultaneous leases, sends during both switches, and records failed probes; its synthetic fixture settings must never be used on the production database.
