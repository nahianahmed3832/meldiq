# Griip Message — Security model (internal beta)

> **Status:** internal beta. The protection described here was built from vetted library primitives,
> and it has been exercised in the tests listed in `TESTING.md`. **It has not been independently
> reviewed. Do not use it for highly sensitive company information** until the gaps in §4 are closed and a
> review has happened.

## 1. What the relay server can and cannot see

| Data | Server sees it? |
|---|---|
| Message text, attachments, reactions, edits, deletions, pins, read receipts | **No.** These are encrypted on the device before upload (§3). |
| Call audio, video and screen share | **No**, when media E2EE is on, which is the default (§7). Without it, only DTLS-SRTP protects media in transit, so the SFU could read it. |
| Account identity public key, device public keys, usernames, display names | Yes. These form the public directory. |
| Organisation structure: org, branch, department and team names, channel names and topics, memberships, roles | Yes. The server needs them to enforce authorisation. |
| Who sends to which conversation, when, how large each message is, the recipient device list | Yes. This is routing metadata. |
| IP addresses, online status, typing indicators | Yes. |
| Delivery receipts (that a device received a message) | Yes. These are generated by the server. |
| Push wake-ups (optional, §7c) | The server stores each opted-in device's push endpoint and knows when it woke it. The push server (our own ntfy) learns only the endpoint's random topic and when it was woken: **no content, sender, conversation, call or key.** |
| Message history | **Ciphertext only.** Relayed envelopes sit in a temporary queue for at most 7 days and are deleted when the recipient device acknowledges them (`RETENTION.md`). Since 2026-10-17 each account's devices also keep its history on the server, encrypted with keys derived from the account identity seed under opaque tags; the server sees item counts, sizes and times, not content or ids (`MESSAGE_HISTORY.md`). |

Encryption does not hide metadata. A relay operator can see who talks to whom, when, and how much.

## 2. Identity and devices

- **Account identity key:** an Ed25519 key generated on the phone. Its 32-byte seed is the **recovery key** that the
  user can display in *Profile → Security*. The server stores only the public key.
- **Device keys:** each device has its own Ed25519 signing key and its own X25519 encryption key for HPKE.
  A **device certificate** binds them to the account. It is an Ed25519 signature by the identity key over
  `griip-device-cert-v1\n<identityKey>\n<signingKey>\n<encryptionKey>`.
  The server verifies the certificate when a device is registered. Every client verifies it again before encrypting to
  that device or trusting it as a sender.
- **Authentication:** challenge–response. The server issues a single-use nonce that expires after 2 minutes. The device signs
  `griip-auth-v1\n<purpose>\n<nonce>\n<signingKey>`. A session token (256-bit random) is returned, and the server stores only its SHA-256 hash.
  Tokens last 7 days, and the app re-authenticates automatically by signing a fresh challenge. Knowing a username grants
  nothing. Tested in `server/test/auth.test.ts`.
- **Private key storage:** private keys and the session token are sealed with AES-256-GCM using a
  **non-exportable Android Keystore key**, which is hardware-backed where the device supports it. Only that ciphertext is written to
  SharedPreferences. Android backup and device transfer are disabled for keys and the database (`data_extraction_rules.xml`).
- **Linking a new device:** the new phone generates its device keys plus an ephemeral X25519 transfer key and shows a
  10-character code. The existing phone looks up the request, shows the new device's key fingerprint, and on
  approval signs a certificate and seals the identity seed to the transfer key with HPKE. The server only relays
  ciphertext. The new phone verifies that the decrypted seed matches the account identity key before using it.
- **Revocation:** any device of the account can revoke another. The revoked device's sessions and queued envelopes are deleted
  immediately, its WebSocket is closed, and other users are told to refresh their key lists.
- **Recovery:** the recovery key restores the *identity* on a new phone, and (since 2026-10-17, where the server keeps
  history) the encrypted message history too, because the history keys are derived from the identity seed. So the recovery
  key now protects the whole stored history: anyone with it and access to the account's server data could read it. Keep it
  offline. If the user loses every device and the recovery key, the account and its history cannot be recovered by anyone. A server
  administrator cannot impersonate a user: there is no server-side master key, and a new identity key triggers
  "safety number changed" warnings for contacts.

## 2b. Orbit 2.0 accounts: email and password (2026-10-18)

Design and contracts: `ORBIT_2_ARCHITECTURE_2026-10-18.md`; decisions: `ORBIT_2_MOBILE_AUDIT_2026-10-18.md` §6.

- **Two layers.** The email-and-password *account* decides who may sign in and holds sessions. The identity and device
  keys above still decide who can read messages. A password never decrypts anything, and the server still can't read
  messages, files or call media.
- **Passwords** are hashed with scrypt (N = 2^15, r = 8, p = 3, 16-byte salt; parameters stored with the hash and raised
  at sign-in). Minimum 10 characters, maximum 128, not the email. Production refuses a lower cost
  (`PASSWORD_SCRYPT_LOG_N`). Passwords are never logged; request bodies aren't logged at all.
- **Sessions:** a 15-minute access token and a refresh token (60 days idle, 180 days at most), 32 random bytes each,
  stored as SHA-256. A refresh token names its session (`<session id>.<secret>`), so every refresh token the session
  ever had is recognised: the current one rotates; the one just replaced gets the same answer again for 30 seconds (an
  answer lost on a mobile network, or several requests racing), so whichever answer the app keeps is the current pair;
  any other one, and the one just replaced after those 30 seconds, revokes the whole session (a copied token, however
  many times the copy was renewed). For that repeat answer the server keeps the last pair it issued, AES-256-GCM sealed
  with a key derived (HKDF) from the refresh token it replaced: a copy of the database alone opens nothing, and the next
  rotation overwrites it (migration 021). Password reset revokes every session; a password change revokes all others;
  removing a device revokes its sessions. The WebSocket re-checks the session on every frame.
- **Clients and racing refreshes (checked 2026-10-19).** Android serialises refreshes: one `AccountRepository` per
  process holds a `Mutex`, and a caller that waited, or comes within 10 seconds of a refresh, uses the new tokens
  instead of refreshing again (the app has a single process). The web app refreshes one at a time per tab (one
  in-flight promise in `AccountSession` and `SetupCredentials`), and only the tab holding the device lock
  (`navigator.locks`) runs an account session. Two tabs can still overlap when "Use here" takes over while the old tab's
  refresh is in flight and the stored access token is within a minute of expiring, both sending the stored refresh
  token; until migration 021 that could end the session, now both get the same pair. On either client, an answer lost for longer than 30 seconds (the app killed mid-refresh, a long timeout) still
  ends the session on the next refresh: the token it kept has become a copy.
- **Enumeration:** sign-up, resend and forgot always answer 202; sign-in answers the same for an unknown email and a
  wrong password after a dummy hash; sign-in throttling is counted per email address whether or not it has an account;
  wrong codes give the same answer whether the address exists, has a code, or has used up its tries.
- **Codes:** email verification uses 6 digits and **must come with the password chosen at sign-up**, so a later sign-up
  for the same unverified address can't take over the account its owner is verifying; an unverified sign-up's password
  changes only together with a new code. Password reset uses 10 characters (about 50 bits). Both expire after 15
  minutes, allow 5 wrong tries and are stored hashed; each account gets at most 5 per purpose per hour, each network can
  cause at most 30 account emails per hour, and the "someone tried to sign up with your address" notice has its own
  allowance, so sign-up attempts can't use up someone's reset emails. A password reset clears the sign-in throttle for
  that address. Emails contain nothing anyone typed (no names). Codes are never logged. `MAIL_TRANSPORT=file`
  (development only, refused in production) writes them to disk.
- **Invite-only servers:** an Orbit 2.0 sign-up takes one use of its registration or organisation invite in the same
  transaction that creates the account; an organisation invite's holder joins that organisation when their encryption
  identity is made.
- **A device joins an account** only with a certificate from the account's identity key: made on the first device,
  derived from the recovery key, or sealed over by another device (pairing). A device that signs in again proves its
  device key, so its session is bound at once. "Start fresh" (no recovery key, no other device) needs the password,
  replaces the identity key, revokes every other device and deletes the server history nobody can decrypt any more;
  contacts see a security-code change.
- **Legacy migration:** the app derives the identity key from the recovery key and signs
  `griip-legacy-migration-v1\n<username>\n<nonce>`; the server checks the signature against the stored identity key and
  issues a single-use, 15-minute ticket (stored hashed). **The recovery key never leaves the phone and is never stored as a
  credential.** Failed proofs are counted per username and per network. Nothing is linked until the proof and the
  ticket both succeed; a link whose email was never verified can be redone, a verified one can't. The phone lets a
  move with a mistyped address start again.
- **On the phone,** the account record and tokens are sealed with the same Keystore key as the identity keys. Signing out
  keeps the encrypted messages and keys for the next sign-in; "Sign out & erase" removes them. A profile holding one
  account's keys refuses another account's sign-up, move or sign-in until it is erased, and keys made for an account are
  reused (after an interrupted setup) only by that account.
- **Known limit:** the account-wide sign-in throttle (50 failures an hour) applies before the password is checked, so a
  distributed guesser can keep a known address from signing in for an hour at a time; a password reset clears it.

## 3. Message encryption: `griip-envelope-v1`

This is implemented in `android/.../crypto/EnvelopeCrypto.kt` and mirrored byte for byte in `server/test/support/griipClient.ts`.

Per message:
1. `contentKey` is 32 random bytes and `nonce` is 12 random bytes.
2. `header` is `griip-envelope-v1\n<messageId>\n<conversationId>\n<senderUserId>\n<senderDeviceId>\n<sentAt>\n<cls>`.
3. `ciphertext = AES-256-GCM(contentKey, nonce, plaintext=JSON payload, aad=header)`.
4. `signature = Ed25519(senderDeviceKey, header + "\n" + b64(nonce) + "\n" + b64(ciphertext))`.
5. For every recipient device (all active devices of all members, including the sender's own other devices), compute
   `HPKE.Seal(base mode, DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-256-GCM; pkR=deviceEncKey, info="griip-envelope-v1/key", aad=messageId+"\n"+deviceId, pt=contentKey)`.

The server verifies the sender signature and checks that the recipient set equals the current members' active devices.
**Exception (API 0.40.0, opt-in per channel):** an AI agent's reader device in a conversation that switched reading on
may also be in the set, never must be. Each sender's app decides from its person's own choice (share or keep), and apps
that don't implement the notice and choice are never shown a reader, so they never wrap to one. Messages wrapped to a
reader are decrypted on the server (its keys are server-held, sealed under `PLATFORM_SECRETS_KEY`), so in those
channels they're readable by whoever controls the server and by the AI provider. Calls are never wrapped to a reader.
Design and limits: `AI_WORKFORCE_2_PLAN.md` phase 5 and `AI_AGENT_CHANNEL_READ_PROPOSAL.md`.
If not, it returns `409 device_mismatch` and the client refreshes keys. The recipient verifies the signature against a device
key whose certificate chains to the sender's identity key, opens the HPKE wrap, then decrypts and authenticates the content.

**Pinned identities are enforced (T1.2, 2026-10-16).** "Identity key" above means the key **pinned on first contact**,
not whatever the server returns now (`KeyDirectory`; the reference client does the same).
- If the server later presents a different identity key for a contact, that contact is *untrusted*:
  - **sending** to any conversation they're in (DM, group or channel) is paused. Messages show "Paused: a security key changed", and nothing is encrypted to the new devices;
  - **incoming** envelopes from them are **quarantined**: stored locally, acknowledged, and not displayed.
- A banner in the conversation offers *Review*. Accepting pins the exact key whose safety number was shown, not a fresh
  server answer, so a second swap is caught too. It then sends the paused messages and opens the quarantined ones.
- If the server goes back to the pinned key, trust is restored automatically.
- This replaces the audit's finding that pinning was warning-only.

**Libraries:** BouncyCastle 1.79 (HPKE per RFC 9180, Ed25519 per RFC 8032), platform JCA AES-GCM on Android, and
`@hpke/core` 1.9 plus Node `crypto` in the test client. **No primitive is implemented by us.** The *composition* is ours and
has not been reviewed. It sits behind the replaceable `MessageCrypto` interface, so that Signal Protocol or MLS can be swapped in later.

Interop between the Kotlin and Node implementations was verified on a physical phone in both directions (`TESTING.md` §3).

## 4. Known gaps (read this)

- **No forward secrecy and no post-compromise security.** Content keys are wrapped to long-term device keys. If a device's
  X25519 private key is stolen, every message ever wrapped to that device can be decrypted, provided the attacker also captured
  the ciphertext (the relay keeps it for at most 7 days). Signal's Double Ratchet and MLS fix this. Neither was integrated in
  this beta (`DECISIONS.md` D-04).
- **Trust on first use.** The first identity key seen for a user is pinned, so a key substituted *before* first contact
  isn't detected. Users can compare safety numbers in person (*Contact → Safety number*) and mark contacts as verified.
  A later change pauses messaging with that contact until the user accepts the new key (§3).
  - A legitimate re-registration (a lost phone without the recovery key) therefore needs every contact to accept the new key.
  - In a large channel, one member's change pauses sending there until the user accepts it, because the server requires
    every member device in the recipient set.
- **Group membership is server-asserted.** The server decides who is a member of a group or channel. A malicious server could add
  a member, with their own certified devices, and that member would receive future messages. Clients encrypt only to devices certified
  by members' identity keys, and pinning stops fake devices for known users, but clients don't independently verify the membership
  list. Fixing this needs MLS-style signed group state (`DECENTRALISATION_READINESS.md`, items 3–4).
- **Deletion and editing are cooperative.** A modified client can ignore delete or edit requests.
- **Read receipts and typing** are visible to conversation members. Typing and online status are visible to the server.
- **Session tokens** are bearer tokens. With the debug build's `http://` mode (testing only) they are exposed on the network.
  Production uses TLS (`https://msg.griipbuddy.cloud`).

## 5. Safety numbers

The fingerprint of an identity key is `SHA-256(identityKey)`, split into six 5-byte chunks, each taken mod 100000 and zero-padded to
5 digits. The safety number for a pair of users is the two fingerprints sorted and joined with a newline, so both phones show the same value.

## 6. Local storage

- The Room database is encrypted with **SQLCipher 4.12** (AES-256). Its 256-bit random passphrase is sealed by the Keystore key.
- Downloaded and sent attachments are written to app-private storage (`filesDir/attachments`). They rely on Android
  file-based encryption, not SQLCipher. "Sign out & erase" first revokes the device on the server (T1.9), so contacts stop encrypting to it, then deletes the keys, the database and the attachments. If the revocation can't be confirmed, the user is told and decides whether to erase anyway.
- Plaintext of unsent messages lives only in the encrypted database's outbox table.
- **Notifications (T4.4):** message notifications show decrypted text and are private on the lock screen ("New message" only).
  The few recent lines a notification shows are held in memory, never on disk. *Reply* and *Mark as read* require the phone to be
  unlocked, go only to the app's own non-exported receiver, and *Reply* is offered only where the user may post. "Sign out & erase"
  now also removes message notifications, so decrypted text doesn't stay in the shade.

- **Server profiles (2026-10-16, ADR 0002):** each server account on the phone has its own Keystore key
  (`griip_master_v1` for the first account, `griip_master_v1_<id>` for others), its own sealed identity and session preferences,
  its own SQLCipher database and passphrase, and its own attachment folder. Profiles never read each other's keys; switching
  closes one and opens the other; identity keys are never copied between servers. The profile list (`griip_profiles`) holds only
  random ids, server addresses and the active id, unencrypted in app-private storage. Erasing or removing a profile deletes its
  Keystore key, preferences, database and files, and nothing of the other profiles.
- **Voice messages:** a recording is written to `cacheDir/voice/` (app-private) while it's recorded and previewed, then deleted
  when it's sent, cancelled or abandoned; leftovers older than 6 hours are removed. Once sent, the clip is an ordinary encrypted
  attachment (same keys, hashes and storage as files).

## 6b. Scanned QR codes

- The in-app scanner (T4.2) decodes frames on the phone and accepts **only Griip invite codes** (`InviteCodes.fromScan`). It never
  opens a URL from a QR code, and `griip://invite` deep links pass through the same parser. A scanned code only fills the join form;
  joining still needs the invite preview and an explicit tap.

## 7. Call media

- Calls use LiveKit 1.13.10 (self-hosted SFU) with the official LiveKit Android SDK 2.29.0.
- **Media E2EE:** the caller generates a random 256-bit key per call and sends it to the conversation's devices
  **inside a `griip-envelope-v1` encrypted control message** (`call_invite`). It is never sent through the call API, a URL or a token.
  Every participant sets it as the LiveKit shared key (AES-GCM frame encryption with PBKDF2 key derivation, the SDK default).
  If E2EE is enabled and the key hasn't arrived after about 10 s, **the app refuses to join instead of downgrading**.
  The first key received for a call is kept, so a later `call_invite` for the same call can't replace it.
  **Since T5.2 (2026-10-16), a key is accepted only from the call's creator**, in the call's own conversation: the app looks up the
  call (`GET /v1/calls/:id`) and compares `createdBy` with the envelope's signed sender. Keys from other members are ignored and logged.
  If the lookup fails for a reason other than 404, the queue item is redelivered and checked again; it is never accepted unchecked.
- **E2EE status badge:** fed by `FrameCryptorGuard`, a crash mitigation that replaces only LiveKit's frame-cryptor *status* observer
  (`KNOWN_ISSUES.md` › Calls). Frame encryption itself, the cryptors, key provider, key index and enabled flag, is untouched.
  - **"End-to-end encrypted" needs proof (D-17, 2026-10-16):** every live track has encrypted or decrypted a frame with our key
    (WebRTC's OK or KEY_RATCHETED), including at least one remote track.
  - Missing-key, encryption, decryption and internal errors show "Encryption problem".
  - Anything else shows "Verifying encryption…".
  - **Limit:** with LiveKit's default `failureTolerance` (-1), a frame that fails to decrypt is dropped without a report. A
    wrong-key peer is therefore shown as not verified, not as an error. Confidentiality isn't affected: its media can't be
    decrypted.
- **Late joiners (T5.3):** a device that has no key for a call it is joining sends a `call_key_request` control in the call's
  conversation. Only the call's creator answers, re-sending the same key inside a `call_invite` to the conversation's current
  member devices, the same audience the server admits to the call. Requests and answers are paced (1.5 s grace, then at most
  every 5 s per call), and ended calls are never answered.
- **Verified:** on the production SFU, a participant with the correct key decoded video and audio, and a participant with a wrong key
  decoded nothing (`TESTING.md` §4).
- **Gaps:** the key is not rotated when participants leave or join. A removed member who still has the key could decrypt
  media *if* they could also obtain the SFU-forwarded packets.
  **Removal from calls (T1.3, implemented 2026-10-16, not yet deployed):**
  - When someone loses membership of a conversation (removed, leaves, removed from the org, branch or team, or demoted
    to Guest), the server removes all their devices from that conversation's live LiveKit room. It also does this when one of
    their devices is revoked or their account is disabled. The person's devices are told the call ended (`endReason: "removed"`).
  - `join` and `connected` return 404 for them.
  - Their LiveKit token can stay valid for up to 10 minutes, and LiveKit can't revoke it. A rejoin with that token is ejected as soon as
    LiveKit's webhook arrives, and in any case by the 60 s reconciliation job, which also repairs removals LiveKit missed while unreachable.
  - Until deployed, production still has the audit's finding (probe P3).
  The key is per call and is deleted from the device 24 h after the call ends.
- LiveKit tokens are JWTs scoped to one room, valid for 10 minutes, and issued only to conversation members.
- **Call reachability (2026-10-16):** ring recovery reads `GET /v1/calls/active` (only the user's own conversations); `POST /alerted` tells
  the caller that a callee device is ringing (members only, not the caller, once per call), and a busy decline tells the caller the callee
  is in another call. These reveal device activity to the people you share the conversation with, similar to delivery receipts. No key,
  token or address is logged; the new call diagnostics record timing, flow state and the candidate *type* only.

## 7b. Public server information

`GET /healthz` and `GET /v1/server-info` are unauthenticated by design (the app checks a server before any account exists). They
return version, client API range, registration mode, an optional instance name, whether calling is configured, and limits. Since
2026-10-17 they also return the `features` list and, when push wake-ups are on, the allow-listed push hosts
(`push.unifiedPushHosts`, a public DNS name). They don't return secrets, file paths, usage numbers or user data
(`server/test/server_info.test.ts`). The LiveKit API secret, the database and the operator CLI are never exposed to the app or the network.

## 7c. Push wake-ups (2026-10-17, off unless configured)

Design and deployment: `BACKGROUND_DELIVERY.md`.

- **What a wake-up is.** An HTTPS POST with an **empty body** to the device's UnifiedPush endpoint, with transport headers only
  (`TTL`, `Urgency`, a fixed `User-Agent`; checked on the wire in `server/test/push_transport.test.ts`).
  - It never carries message content, sender or conversation ids, message ids, call ids, keys or tokens.
  - The app never reads a push's content. It fetches its queue over its own authenticated connection, where envelopes are verified
    and decrypted as always.
  - A forged wake-up (from anyone who learned an endpoint) can therefore only make the app check for messages.
  - On the phone, the connector library's exported receiver accepts distributor events only with this registration's random
    token, and hands them to Meldiq's service, which isn't exported.
- **What each party learns.**
  - Meldiq's server stores each opted-in device's endpoint (a random ntfy topic URL) and records when the push server accepted a
    wake-up (`push_endpoints`).
  - The push server, our own ntfy, sees the topic, the API's address, the phone's address while it's subscribed, and the times of
    wake-ups. It doesn't see who wrote, in which conversation, or how much.
  - Wake-up timing does reveal when a device had something waiting. Meldiq's server already knows that.
- **No SSRF.**
  - Endpoints are accepted only as `https://` on a host (and port) listed in `PUSH_UNIFIEDPUSH_HOSTS`, without credentials or
    fragment. They're checked again before every request, so removing a host from the list stops (and drops) its endpoints.
  - Before each request the host name is resolved. If **any** address is loopback, private, shared (CGNAT), link-local (cloud
    metadata), multicast, reserved or documentation space, or anything other than global unicast for IPv6 (IPv4-mapped addresses
    included), nothing is sent.
  - The request then goes to the address that was checked (pinned), so DNS can't move it afterwards, with TLS verified against
    the host name.
  - Redirects are never followed. Each request has a 5-second deadline (`PUSH_TIMEOUT_MS`), no response body is read, at most
    8 requests run at once and at most 1,000 wait.
  - Tested in `server/test/push_wakeup.test.ts` and, on the wire, in `push_transport.test.ts`.
- **Abuse and battery.**
  - Wake-ups are coalesced to one per device per 30 s, with later requests deferred rather than repeated. A ring may follow the
    previous wake-up after 5 s.
  - Someone who messages or calls a person a lot therefore can't wake their phone more often than that.
  - Delivery receipts never wake a phone.
- **Logs.** A failed wake-up logs the device id and a reason code (the push server's status such as `http_507`, or `timeout`,
  `blocked_address`, …). Endpoints, push hosts and response bodies are never logged.
- **Lifecycle.** An endpoint is removed:
  - when the device withdraws it, revokes itself, is revoked, or signs out;
  - when the push server answers 404 or 410;
  - after 7 days of failures;
  - when its host leaves the allow-list;
  - by the retention job, for revoked devices.

  Disabled accounts are never woken.
- **Residual risks.**
  - Endpoints are stored in plain text in the server database. With the database, someone could wake opted-in phones, but not
    read anything.
  - A phone's distributor might use another ntfy server, for example the public ntfy.sh. The allow-list refuses those endpoints and
    the app tells the person which server to set.
  - Distributors that require VAPID (RFC 8292) or encrypted payloads aren't supported. ntfy needs neither.

## 8. Server hardening

- Every route validates input with zod. Body limits apply (256 KiB default, 2 MiB for messages, 25 MiB for attachments).
- **Registration is invite-only by default (T1.6).** A new account needs either a registration invite or a valid org invite.
  - Registration invites are issued only by the operator CLI.
  - Org invites are minted only by authenticated org managers.
  - Codes are 60-bit random and stored as SHA-256 hashes. Uses and expiry are bounded and enforced inside the registration transaction.
  - Residual risk: anyone who can create an org can invite people into it, and so let them register.
- **Route audit (2026-10-16):** every route requires a session except registration, login, challenge, device-pairing bootstrap and the
  signature-checked LiveKit webhook. Each resource route checks membership or role in `authz.ts`. Two deliberate openings to revisit:
  - anyone can add any user to a new group without consent;
  - device public keys can be looked up for any user id. They are public key material by design, but they reveal how many devices a user has.
- **Presence privacy (T1.7):** online state and last-seen are shown only to the person, to anyone sharing a conversation
  with them, and to non-guest members of a shared org (`Authz.canSeePresence`). Knowing a username or id reveals nothing;
  realtime presence events go only to DM and group peers.
- **Upload quotas (T1.6):**
  - Attachments stream to disk; nothing buffers a whole file in memory.
  - Limits: per-user daily and stored bytes, a server-wide byte cap (`507`), and per-user and global concurrent uploads and in-flight bytes.
  - Partial files from interrupted uploads are deleted, and stale ones are removed at startup.
  - Containers have CPU, memory and process limits.
  Rate limits are global per device or IP, with tighter limits on auth and invite endpoints.
- Authorisation is enforced on the server for every resource (`server/src/authz.ts`). Non-members get `404` to avoid
  leaking existence. Tested with direct API calls in `server/test/orgs.test.ts`.
- All IDs are 128-bit random. Invite codes are 60-bit random, stored hashed and rate-limited. Attachment downloads require
  membership of the conversation they were uploaded to.
- Logs never contain request bodies, Authorization headers or message content.
- There is no admin HTTP surface. Operator commands run through `docker compose exec api node dist/admin.js`.
- The API and LiveKit signalling bind to `127.0.0.1` behind the host's nginx TLS. Only LiveKit's media ports (7881/tcp, 7882/udp) are public.

## 9. Federation

Federated servers, core nodes, metadata and the threat model: `SECURITY_AND_PRIVACY.md`. Envelopes, keys and storage on devices are as
described above; nothing in federation decrypts or re-encrypts content.
