# PostgreSQL compatibility cutover

The owner selected the existing Frankfurt project `bkvlxbsnzqkhbifawcww` for the eventual production database on November 3, 2026, and confirmed publishing their own production-signed Android release. This authorizes the final data sync and database switch after verification. Atlas and its backups must be retained. This document does not attest that cutover has occurred.

The first production phase preserves the released account/device authentication, Fastify HTTP/WebSocket protocols, S3, Hostinger, LiveKit, Redis and push integrations. Native Supabase Auth and Realtime activation remain separately blocked until their identity, client and revocation checks pass. The existing Stockholm social-login project `sgowwdmnavcsofzlgggm` is distinct from the Frankfurt database project; its `SUPABASE_URL` and social credentials must not be overwritten with database settings.

Startup uses `DATABASE_MODE=supabase`, `SUPABASE_DATABASE_URL`, `SUPABASE_DATABASE_PROJECT_REF`, `SUPABASE_DB_CA_FILE`, `SUPABASE_DATABASE_POOL_SIZE` (2–6), and `SUPABASE_PRODUCTION_ACCEPTANCE_FILE`. The database URL must identify the selected direct or session-pool endpoint; transaction pooling and TLS overrides are rejected. Production also requires Redis. Missing PostgreSQL injection cannot open a legacy SQLite authority. Hosted application startup requires a restricted login inheriting `meldiq_api`, without elevated database privileges.

The compatibility composition selects legacy delivery explicitly: messages remain in PostgreSQL and the existing durable per-device relay/push path serves them. It does not accumulate a second set of native Realtime/push jobs for later duplicate delivery. Dedicated native transport tests continue exercising the transactional outbox independently. API parity can select this production phase using `MELDIQ_TEST_PG_DELIVERY_MODE=legacy` alongside the owned loopback test URL.

The acceptance JSON is an enduring, private regular file, supplied only after the actual checks. It records version 1, projectRef, mode `database-compatibility`, legacyProtocols true, runtimeRevision (40 hexadecimal characters), sourceSha256 (64 hexadecimal characters), acceptedAt (ISO timestamp), and the true verification results destinationReconciled, encryptedBackupVerified, rollbackPrepared, and operatorAccessVerified. Never manufacture these results to enable startup. The accepted source fingerprint must exist in the destination migration ledger. Acceptance survives ordinary service restarts; it does not expire after deployment.

Production starts with a separate activation hold. Until the private operator command `database-cutover-activate <exact-source-sha256>` succeeds, customer requests answer maintenance and scheduled/background effects remain deferred. Health, server information, site details and selected read-only operator checks stay available. Activation durably writes `/data/database-authority.json` before starting background effects and releasing requests. This is the authority commit point. Ordinary restarts read that same source-bound receipt and resume PostgreSQL; they do not enter maintenance again. Read-only rehearsal holds cannot activate. Operator status is available through `database-cutover-status`.

Before this durable activation, the ingress freeze and held background work preserve a controlled rollback window to the retained Atlas deployment. After activation, retain PostgreSQL and use a validated PostgreSQL-compatible rollback image; do not resume Atlas unless every post-cutover change has first been transferred and reconciled. A background startup failure after the authority receipt is written leaves PostgreSQL committed and the service held for repair. The source, destination and authority receipts must be retained with the rollback evidence.

In PostgreSQL mode, `node dist/admin.js <command>` connects to `/data/.ops/socket`, inside a directory owned by the application UID with permissions 700; the socket has permissions 600. Commands run through the active process's repositories and writer lease. No TCP administrative listener or second cache writer is created. Command output stays on the private IPC connection. Legacy MongoDB/SQLite conversion commands fail closed in this mode; they remain available in the retained offline legacy tools. Use the host encrypted PostgreSQL backup utility for database recovery instead of the SQLite-only backup command.

Before switching traffic, verify the exact release artifact, hosted restricted-role startup, operator access, protocol parity and load, final frozen-source reconciliation, encrypted recovery and recurring backup/mirroring. Retain the data volume, reports key, platform encryption key, social credentials and S3 local fallback. After accepting PostgreSQL writes, reverting the application to an older Atlas snapshot would lose those writes; restore or reverse-transfer the new writes before changing authority again.

Current checkpoint: the newer read-only source snapshot has 678,701 application records across 282 tables. Its complete local import, resume and row/financial/timestamp/counter reconciliation passed. Repository bootstrap on the owned MacBook clone took about 1.08 seconds with roughly 393 MB resident memory; this is not a hosted/VPS performance measurement. The earlier Frankfurt rehearsal remains separate until the final reviewed sync procedure is ready.

The actual Node22 VPS probe initially exceeded 180 seconds because 500-row cursor pages caused excessive Frankfurt round trips. Streaming row events into the cache while batching eight SELECTs reduced verified restricted-role bootstrap to 13.365 seconds, using 252,280,832 resident bytes; a simple query round trip measured 168 ms. The source fingerprint and cached critical table counts matched, with zero data writes, legacy SQL attempts or connection errors. A separate owned local rehearsal verified all cached table counts across the 678,701-record snapshot. This does not establish API load or mobile acceptance by itself.

The scheduled backup now dispatches according to the live container's database mode. `scheduled-atlas-backup.py` preserves the previous installed implementation; `scheduled-postgres-backup.py` exports a read-only PostgreSQL snapshot with a pinned official PostgreSQL 17.11 client, verified TLS and age encryption. Its private operator settings stay outside Git and outside the application container. It also preserves deployment settings, reports/encryption configuration, local fallback attachments and profile media. The existing daily timer remains active. `--rehearsal` reads the approved Frankfurt destination before cutover while Atlas is still live; it does not switch authority.

The first VPS PostgreSQL backup at `20261102T234449Z` passed full encrypted-payload authentication and dump parsing. The off-host mirror authenticated all ten encrypted payloads. `verify-postgres-mirror.mjs` independently restored an owned MacBook loopback database and matched all 317 table fingerprints/678,057 rows, then removed its scratch database. Its result explicitly excludes full Auth/Realtime/OAuth/SMTP service restoration. When running this verifier from the web operations checkout, set `MELDIQ_SERVER_DIR` to the isolated backend's `server` directory. The recovery identity and archives remain in private files outside Git.
