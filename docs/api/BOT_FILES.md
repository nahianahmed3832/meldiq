# Native bot encrypted files

Implemented candidate source; full coordinated release acceptance is still open. Community file access uses two new requested/approved scopes: `files.upload` and `files.read`. Existing message/history approvals do not gain them automatically. Uploads additionally need current native posting/attachment authority. Publication needs `messages.post` plus `files.upload`. Personal bot chats remain text/interactive-message only in this preview.

The bot namespace adapts the owning file controller: streamed ciphertext upload, direct single/multipart upload sessions, URL refresh, part signing/listing, completion, cancellation and ranged ciphertext download. It shares the native quota lock, reservations, plan limits, checksums, completion idempotency and abandoned-object cleanup. No storage provider, region, pricing or quota changed. Presigned URLs already issued to storage have their native short lifetime; current API authority is still required for renewal, completion and publication.

Downloads require current credentials, installation identity, explicit file approval, channel membership and native history boundaries. Pending objects remain private to their uploader. Bot downloads stay on the native API stream, without a human session/media grant or a credential-bearing redirect. Admission is rechecked after asynchronous storage access and between streamed chunks. Revoked streams close rather than completing a file; callers must discard incomplete downloads.

The bot uploads native encrypted bytes and posts the same validated reference used by other clients. The shared native descriptor and publication pipeline reject incomplete, expired, foreign-channel, duplicate, size/hash-mismatched files and invalid thumbnails. Publication rechecks current bot/native content authority inside message acceptance. V2 attachment reference keys remain visible to the relay under the existing Meldiq protocol; this is not server-resistant E2EE.

JavaScript and Python provide native upload/session/streaming-download methods. The optional JavaScript whole-object AES-GCM helper buffers at most 64 MiB to bound its own memory. This convenience limit does not alter server/plan entitlements; larger files use native streaming encryption and direct multipart operations. Python remains standard-library HTTP code and expects already encrypted bytes. No hosted execution, automatic mutation retry, plaintext server encryption, content scanner or external cloud acceptance is claimed.

Controlled PostgreSQL tests cover separate consent, native publication, ciphertext interoperability, ranges, channel denial, storage-time rotation, after-lookup revocation and mid-stream withdrawal. Local S3 stand-in tests cover single/multipart completion and cancellation. These are local API/storage protocol checks; actual Frankfurt transfer performance, physical clients and complete release/restore validation remain pending.
