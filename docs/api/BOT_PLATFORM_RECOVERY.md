# Bot platform recovery checkpoint

The broader bot platform is an unreleased candidate. Its requested/approved scopes, personal consent, installation incarnations and derived-credential bindings are additive. Older API source `cc61eb40` has none of those bot approval checks. Replacing this candidate with that predecessor while retaining usable bot credentials would discard an authorization boundary. An ordinary client-only rollback can keep the current authorization API running.

For an API rollback, retain the current schema and later customer state. Stop all writers and jobs, drain media, and verify `meldiq_private.bot_media_evictions` is empty before discarding the runtime. The signed SFU admission handler must remain available during the drain. Removing the API alone does not invalidate provider media tokens. Never restore an earlier database over later writes merely to start old code.

Hold the bot API, developer bot management, interactions and installation route families at the reverse proxy before starting an older API. This includes `/v2/bot/`, `/v2/developer/bots`, `/v2/interactions`, and `/v1/orgs/:orgId/bots`, including their child paths. Inspect the actual nginx location precedence and verify the holds externally; a generic regex include is not evidence that a higher-priority proxy location cannot bypass it. Human authentication, messages, billing callbacks, reports and human-owned integrations retain their existing routes.

With writers stopped, quarantine bot tokens and identities, withdraw active credential revisions, rotate bot-derived webhook hashes and revoke/rotate bot-derived invitation codes. Keep requested grants, personal consent, installation revisions, denial bindings, reports and message history. Preserve human-created credentials and already disabled identities. Reopening bots after a later compatible rollout requires deliberate operator review, fresh developer credentials and the applicable manager/recipient approvals; do not mass-enable previously blocked accounts.

## Local rehearsal

`server/scripts/rehearse-parity-database.mjs` accepts only an owned loopback `meldiq_parity_stage_*` source and a **new** `meldiq_parity_stage_rollback_*` target. It refuses a hosted endpoint, an existing target, an application still connected to the source, and pending bot media cleanup. It never changes its source. It exports a repeatable-read snapshot, encrypts the custom PostgreSQL 17 archive with a newly generated private local age key, independently restores it, compares every table's row count/checksum, schema/index/trigger/policy/grant definitions and sequence state, then rehearses credential quarantine only on the restored target.

`server/scripts/rehearse-parity-recovery.ts` first requires a newly migrated empty recovery-source stage. It uses the real API/domain services to create human and bot identities, reviewed installation scopes, derived and human-owned integrations, a withdrawn personal consent, an encrypted attachment, sealed report evidence and an opaque event cursor. After stopping that application, it invokes the database rehearsal, encrypts/restores the cold runtime files with their modes, and starts the current API against the restored database. It checks returning human credentials, community access, actual live message delivery, original plaintext download, readable sealed report evidence, cursor-key recovery, bot denial and preserved human integrations/withdrawn consent.

Run from `server/` after creating the fresh source with the existing `prepare-parity-stage.ts` helper. Supply explicit local URLs and a new private absolute output directory. PostgreSQL 17, age and tar are required. Database snapshots, runtime files, keys and fixture credentials stay outside Git. Only aggregate receipts belong in release evidence. The scripts preserve the source and restored databases and never delete a prior rehearsal.

An optional fourth argument to the application rehearsal names an extracted tracked predecessor source archive with its `SOURCE.json` identity. The `cc61eb40` source boots against the additive restored schema using the currently installed local dependencies. Human login, community access, live messages and original plaintext downloads pass. Prior bot and derived webhook credentials remain denied even when calling that local old API directly. An owned test proxy refuses four bot route families in six HTTP cases, including encoded paths, without forwarding them, while an ordinary human route succeeds.

These checks qualify local fixture recovery, current source and bounded predecessor-source compatibility on the same owned PostgreSQL cluster. They do not qualify the exact production container/overlay and pinned dependencies, role-global recovery on an empty cluster, actual Frankfurt/S3 recovery, hosted Auth/Realtime, installed clients, production nginx precedence/normalization or rollback after production writes. Those remain release gates. No production rollback or credential quarantine has been authorized or performed by this checkpoint.
