# Bot voice key approval foundation

Candidate source only. Voice media join/leave and encrypted handoff remain active implementation work. This checkpoint alone does not provide working bot voice participation.

The existing developer permission manifest accepts an optional `voicePublicKey`: a canonical base64, 32-byte public X25519 key generated by the bot process, or null to clear it. The API rejects malformed and low-order points. No private key, human account device, session or user WebSocket grant is created. The manifest returns the public key and its SHA-256 fingerprint for review. Omitting the field preserves it.

Every update uses the existing optimistic manifest revision. `approvedVoiceKey` requires current `voice.connect` approval and an installation review of that exact manifest revision. A changed/cleared key therefore cannot inherit prior media approval. Ordinary native scope intersections retain their existing behavior. Native channel/voice bans and connect/speak authority must additionally be checked by the media lease implementation.

SQLite109 and PostgreSQL033 add only nullable public material to `bot_requested_permissions`. No production migration ran. The existing public/native identities are unchanged.

API typecheck passes. Web owner configuration, current fingerprint display, explicit manager listening disclosure, unchanged-scope reapproval and stale-review rejection pass eight real browser cases across Chromium, Firefox, WebKit and phone-width. Physical devices and actual encrypted bot media remain unverified.
