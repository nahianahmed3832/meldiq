# Native bot community voice preview

Implemented candidate source, not deployed or fully accepted. This preview joins an existing active locally hosted community voice call. A compatible Meldiq Web participant must hold the room key. Bot-created rooms and the new Android/Windows handoff/integration remain outstanding qualification work. Personal bot DMs remain messages-only. There is no recording, clips, soundboard, hosted execution or vendor-wire compatibility claim.

The bot's X25519 public key belongs to its requested manifest. Media access requires explicit manager review of the exact current manifest revision, requested/approved `voice.connect`, current native channel membership/connect authority, no ban/timeout, current credential/plan and the same installation incarnation. `voice.speak` and native speaking authority are independently required. A separate `botvoice_` media identity has no account device, user session or user WebSocket grant. Room capacity includes pending bot reservations.

`POST /v2/bot/voice` issues a one-minute initial room token and a 60-second renewable in-memory lease. Tokens start receive-only, with no video/screen/data/metadata publishing. A current compatible human media participant seals the room's32-byte key with the existing HPKE suite, bound to call/channel/bot/lease/manifest revision. The API accepts only bounded ciphertext, stores it only in lease memory, and rechecks the human's current device admission after asynchronous SFU lookup. The bot opens it locally; no plaintext key enters an API request, message history, journal, account draft or database.

The receive grant covers the room’s audio, camera video, screen shares and other in-call content. The microphone restriction applies to publishing, not receiving. Manager review must disclose the full receive capability.

The bot waits for `GET /v2/bot/voice/:leaseId/key`, connects with frame encryption, then calls `POST .../connected`. Actual SFU presence and current permissions are checked before microphone publishing is enabled. The response includes current `canSpeak`. Heartbeats renew only a still-authorized lease; they cannot revive expiry/revocation. `DELETE /v2/bot/voice/:leaseId` closes admission before removal. Signed SFU webhooks recheck bot admission and publishing authority; ended calls reject stale joins.

Rotation, changed approval/key, uninstall, current native restrictions, disconnect, expiry, call end and shutdown withdraw API admission and initiate media removal. The bounded shared maintenance loop retries failed SFU work. PostgreSQL034 adds API-private `bot_media_evictions` containing only lease/bot/call/room/time removal metadata. It is written before issuing media credentials, contains no token/ciphertext/key, is bounded with an advisory-locked capacity check, survives account/call deletion, and is deleted only after confirmed SFU removal. Restart cleanup targets that ledger rather than scanning unrelated rooms. Failed physical removal remains pending; access denial alone is not evidence of media disconnection.

Self-hosted LiveKit does not invalidate a saved token merely because a participant was removed. Meldiq rechecks admission in signed SFU webhooks and removes stale connections; an API refusal is not itself proof of media termination. Failed removal remains pending and retried. Initial JWT lifetime must not be confused with provider-refreshed tokens or instantaneous token revocation. [LiveKit token guidance](https://docs.livekit.io/frontends/reference/tokens-grants/). Local tests reconnect a saved grant after revocation and observe its removal with no received audio frames; they do not prove all provider/failure timings.

The JavaScript client exposes join/key/connected/renew/leave operations. Its optional `voice.mjs` helper uses separately installed HPKE; the main HTTP client remains dependency-free. Python supplies the corresponding HTTP operations. The optional listen-only native example performs no recording/file writes. Generated private keys are non-extractable and volatile; an operator process restart requires new public-key review unless the operator supplies a separately managed CryptoKeyPair. See `server/sdk/README.md`.

Validation evidence is maintained in the Web integration repository under `docs/yapin-parity/part4/evidence`. Real Chromium/Firefox/WebKit/phone-width flows exchange sustained encrypted audio with the native LiveKit SDK, require the browser's verified-encryption badge/BOT identity, and observe actual disconnection after revocation. Control-plane tests separately cover scope/key approval, one-minute initial room grants with microphone-only publishing, pending capacity, actor-device races, HPKE privacy, RLS, expiry, failed-removal retention/retry, orphan/deleted-identity recovery and token rotation. These do not constitute physical-device, hosted-provider geography, load, disaster-restore or complete coordinated-release acceptance.

Rollback/restore must drain bot media and verify the removal ledger is empty before discarding this runtime. A database point-in-time restore also requires the existing media service to be drained/stopped; otherwise sessions created after the snapshot may have no surviving metadata. Additive database structures may remain during source rollback. Production deployment still requires the complete validated coordinated candidate and explicit owner authorization.
